Overview

The WTFT (Where The F***ing Tokens?!) utility provides visual, granular accounting of your session's token consumption and associated monetary cost ($ USD). It parses the active session's append-only .jsonl log, classifies each historical interaction into one of 9 work types, and renders a stacked, color-coded ASCII bar graph over configurable time intervals.

Command Reference

/wtft [options]

Analyze and display the session cost breakdown in a persistent TUI widget below the editor.

/wtft -o, --other

Outputs a cleanly aligned, descending-frequency histogram of the primary executable/command names (e.g., node, npm, cat, mkdir), their execution counts, and cumulative costs during turns classified as "Other". Under the Pi TUI Widget, this prints the histogram directly into the prompt-response message scroll (via chat notification) without modifying the timeline widget. Under the CLI binary, it appends the histogram to stdout directly below the printed timeline.

wtft [options] (Standalone Shell Binary — Cross-Harness)

Run the cost auditor directly from your host shell outside of Pi. Just like bin/merge.mjs, it is shipped as plain ESM JavaScript (bin/wtft.mjs) so it runs on stock node without triggering Node's type-stripping errors. Install it with bin/install-wtft, which builds, then puts four entries in ~/bin: the bundles wtft.mjs and wtft-daemon.mjs as copies, plus wtft and wtft-daemon as symlinks to them (spec-46). The old line here named npm install -g github:duppypro/princess-pi-packages, which is wrong three times over: that repo was renamed to princess-pi-tools, wtft was extracted out of it, and nothing is on npm (#29). You can invoke it as wtft, via the ./wtft wrapper from the repo root, or through Claude Code's ! prefix (e.g. !wtft -w 90 -i 1d). It reuses the exact same classification engine as the Pi extension, but outputs directly to stdout, allowing you to pipe the output (e.g., wtft | less -R).

Classification Taxonomy & Priority Rules

To avoid guessing or misrepresenting untraced exchanges, interactions are strictly classified based on the file paths written or read, or the commands executed, under a strict priority system:

1. Writes take priority over Reads

  • If two or more distinct categories are written, the turn is mixed.
  • If exactly one category is written, the turn is classified as that category (spec, code, tests, or research).

2. Reads Fallback

  • If no writes exist, the same logic applies: multiple categories read becomes mixed, while a single category read becomes that category.

3. Command Analysis Fallback

  • If no files are accessed, but a command is executed in bash:
    • If starting with cat, head, or tail -> extracts file path and dynamically maps to Read Fallback (or Write Fallback if using a heredoc cat << 'EOF' > file redirection).
    • If starting with git -> git.
    • If starting with grep, rg, ripgrep, or find -> grep.
    • Any other commands -> other.
  • If no commands exist, but dialogue text is present -> prompt.
  • Otherwise -> other.
Classification Color Code Trigger Criteria
Spec Work (spec) ANSI Bright Green (\x1b[92m) Touches files under docs/ or matching AGENTS.md, ARCHITECTURE.md, README.md, or contains spec planning keywords. Treats any .md file as spec.
Code Work (code) ANSI Orange (\x1b[38;5;208m) Touches files under .pi/extensions/, extensions/, src/, public/, bin/, or debug/. Treats code and log/data files (e.g., .ts, .js, .jsonl, .json, .sql, .txt, and bare files without extensions) and ignores (e.g., .gitignore, .dockerignore) as code.
Tests Work (tests) ANSI Yellow (\x1b[93m) Touches files under tests/ (the dedicated test suite directory).
Research Work (research) ANSI Magenta (\x1b[95m) Touches files under research/ (prototypes and algorithmic experiments).
Git Work (git) ANSI Cyan (\x1b[96m) Runs git bash commands.
Grep Work (grep) ANSI Blue (\x1b[94m) Runs search tools like grep, rg, ripgrep, or find.
Prompt Work (prompt) ANSI Dim White (\x1b[37m) Conversational prompt and response with no files or commands accessed.
Other Work (other) ANSI Dark Grey (\x1b[90m) Generic commands, default fallback.

SURGE Timeline (24-hour pricing bar)

The title line renders a 24-hour timeline showing DeepSeek peak-valley surge pricing windows. Orange segments mark surge-priced hours, green segments mark normal-priced hours. The schedule is DEEPSEEK_PEAK_WINDOWS_UTC_MINUTES in extensions/lib/wtft-cost.ts, weekday-gated by DEEPSEEK_WEEKEND_OFFPEAK_FROM (#495); the hours themselves are not re-typed here — the Model Pricing section below renders them from the generated manifest. The bar is coloured by asking getDeepSeekPeakMultiplier what each hour costs, so no hour is coloured differently from the way that hour is billed. It paints the schedule for the day containing now, while the bins beneath it may be older — on a weekend the bar shows no surge hours even where weekday bins are still flagged. Which day the bar should describe is #496. The timeline uses ─ box-drawing horizontal rule characters (U+2500) for a continuous unbroken line.

Markers: The current hour displays a clock-face emoji (🕐–🕛, hour % 12) — including the noon hour (🕛 at 12:00p–12:59p). Solar noon is a separate ☀️ glyph between hour 11 and hour 12, so every hour keeps its own slot: 12 hour-slots left of the sun, 12 right (#7). The timeline is bookended by the current moon phase emoji (🌑–🌘, computed from synodic-month formula anchored to 2026-07-14 new moon with half-phase centering).

Badges: When in or near a surge window, a badge is appended: ⚡ SURGE 2x (active), ⚡ SURGE APPROACHING (within 20 min of start, blinking orange), or ⚡ SURGE ENDING (within 20 min of end, blinking green).

Cache Miss divider: When a parent turn re-primes its prefix instead of reading it — cache_read_input_tokens 0 with cache_creation_input_tokens above 0, or a recache the overhead split finds, where only a small prefix stayed cached (#241) — a ── Cache Miss ── divider line with tick-position ┼ markers is drawn directly below that bin's row (rows are newest-first, so it separates the missed turn from the older turns whose cache it could not reuse) — always shown, even with --no-ticks, and in turn-based intervals as well as time-based ones.

This is observed, not predicted. Until #152 the divider was inferred from elapsed time against the 5m/1h TTL and was labelled Cache Expired; that model could not see invalidation which consumed no time — a model switch, a system-prompt edit — and was disabled entirely for turn-based intervals (#121). The label says "Miss" rather than "Expired" because the usage block proves the re-prime happened but says nothing about why, and TTL is only one of the causes.

The flag is computed before the tag is written (Interaction.cacheMiss, tag field miss, introduced at tagger v2.7.0): the zero-read case at parse time, the recache case where the overhead split runs, since it needs the previous turn's context. Not at render time, because the compaction/recache meter-split writes cr and cw onto two separate tag lines, so the original pair is gone from the tag, and the recache case also needs the previous turn's context. A session's first turn is marked when it reads no cache at all. One that finds a small shared prefix already cached is not, because the recache rule needs a previous turn to compare against. Since tagger v2.11.0 a partial re-prime, where a small prefix survives, is marked too, by the overhead split's own recache rule (spec-241).

Sidechains are not marked (#115, gated from tagger v2.8.1). A Task subagent starts with an empty context, so read-0 / write-everything is how it begins rather than something it lost, and flagging it made the divider noise that grew with fan-out. The divider is parent-only, matching the exclusion splitOverheadCost already applies to recache detection. It is gated twice, because the two harnesses mark a subagent differently: Claude Code stamps isSidechain on every turn of a subagent transcript, which the parse-time rule reads, while Pi marks one at file level with a parentSession header and no per-entry flag — so the flag is cleared again from provenance, for anything that came out of a subagent transcript at all. That clear is one exported seam, clearSubagentCacheMiss, called from two readers that must stay in step — loadSubagentInteractions (the CLI and Pi widget read path) and the daemon's syncSubagentTranscript (which writes the tag file the CLI renders from). Clearing it in only one bakes miss: 1 into the tag file and makes the two disagree about the same session. No isSidechain field was added to the tag wire format; the gate runs before the tag line is written. The recache case (#241) is decided while the session's own lines are serialized, and subagent lines never pass through that split.

Unified in buildWtftLines: Both Pi widget and CLI (non-watch and --watch) share one code path. The Pi widget passes the session model explicitly; the CLI auto-detects DeepSeek from classified interactions. Non-DeepSeek models render an all-green timeline with no badges.

TUI Visualization Style

The TUI offers two distinct high-fidelity visualization styles depending on the display mode:

  • Cumulative Mode (Stacked Bars): Renders a stacked, horizontal binned bar representing overall running cost over time. Each category's segment is allocated characters from its absolute cumulative cost against the global scale-maximum, guaranteeing monotonically non-decreasing bar widths — a category's segment can only grow, never shrink, matching the mathematical guarantee that cumulative subtotals increase (#106).
  • Bucket Mode (Scatter/Multi-Line Plot): Acts as a non-stacked point-of-spend multi-line chart. Each category is evaluated independently, placing exactly one colored marker block at its absolute visual position on the scale. Categories that did not spend anything in that interval are omitted. To resolve overlap conflicts where multiple categories happen to fall onto the same horizontal index, characters are plotted in the reverse priority of the legend (from right to left, i.e., Other -> Spec) ensuring that more critical categories like Spec always overlay and sit on top of others.

Legend indicators are placed dynamically on the top title row (or on the second row if the terminal width is narrow), completely removing the redundant 'Legend:' prefix as it is self-evident.

To maximize space and minimize vertical height, the ticks scale and dollar labels are collapsed into a single, ultra-clean horizontal row (when ticks are enabled). The dollar labels themselves (e.g. $0.00, $scaleMax/2, and $scaleMax) are embedded directly inside the horizontal box-drawing line and styled as inverted blocks. To ensure the date indicator on this top ticks row aligns perfectly with the rest of the visual hierarchy, it is styled identically to the standard day-change separator rows (Dark Grey/Bright Black) and rendered as ─── Mmm-DD ─── leading directly into the dollar scale line.

Architectural Design

1. Log parser daemon: wtft-daemon classifies each interaction and writes pre-computed entries to a harness-agnostic tag file (wtft-tags/<session>.wtft-tag.v<WTFT_TAGGER_VERSION>.jsonl). A session under the Claude projects root or the Pi sessions root is served by that root's one process. A session outside those roots keeps its own process. Costs are rounded to 6 decimal places (micro-cent precision) before serialization to eliminate float drift between the widget's in-memory subagent parse and the file-based CLI. In Pi, the widget reads the session's own turns from the tag file (readTagFileWithVerdict, since #176), the same file the CLI reads, and spawns a daemon on session_start to keep it warm. After 24h with no new lines, a per-session process exits, and the Pi agent_end handler checks health via checkDaemonHealth and starts one again. A harness process stays up and drops that session with its lease; the next request adopts it again. A harness process reads only the sessions a reader asked for, and what they spawned. It flushes a session's own turns before reading its subagents, so a report shows that sum at once, marked provisional until the subagents are in. On version bump, the new daemon detects the old-version tag file and auto-replaces the old daemon — no manual restart needed.

2. Binning Engine: Groups entries by their timestamp into chronological bins based on the requested interval (e.g., 6-minute windows for granular auditing, or 1-day windows for multi-day tracks).

3. Scaling & Layout: Normalizes the absolute length of each interval's ASCII bar based on the maximum cost in any single interval (typically capped at 30-40 characters wide to fit standard terminal outputs gracefully). Each sub-segment within that bar is allocated its proportional share of characters based on its absolute cost contribution, without rendering percentages or additional trailing text.

4. Recursive Subagent Rollup: When a Claude Code session log is targeted, WTFT auto-detects if a subagent directory exists (e.g., <session-id>/subagents/). If present, WTFT recursively reads all subagent .jsonl logs and blends their interactions chronologically based on their individual timestamps. This guarantees that binned timelines and other command histograms represent the true, cumulative cost and work allocations of the entire multi-agent session tree.

5. The Scoped Session Picker (#89): When running WTFT without an explicit session path option, WTFT discovers session logs SCOPED to the current directory by default — a folder-name match alone (any encoding, see 5b), no whole-repo scan, no cross-directory lookup — and to the last 20 minutes. That default is what makes a plain launch cost a handful of stat calls rather than a scan of every transcript on the machine (measured 2026-09-18: ~7 ms against the pre-#89 default's 2.0 s warm on an 11,005-transcript corpus). The selector display shortens the path to a compact form: ~/g-p/<project>/<date>...<uuid-tail> where g-p is the first-letter shortening of git-projects. The project name is kept in full, with one exception: a git worktree checkout compacts to <repo>/w/<branch> (so worktrees-demo-99-branch renders as demo/w/99-branch) — otherwise every worktree row reads as an unrelated project with a very long name. UUIDs are truncated to the last 4 hex characters. Session age is shown as a relative time (e.g. 2h ago, 3d ago).

  • Interactive Picker (TTY): If standard input AND the stream the picker draws to (stdout normally, stderr under --json) are both real terminals, WTFT renders the interactive picker — even under --json, drawn to stderr there so stdout stays one clean JSON document — showing the compact path, estimated cost, turn count, harness, and relative time. j/k/arrows navigate (wrapping the whole list, sliding an 11-row window past 12 candidates, with a "12-22 of 40" position line), Enter selects, q/Ctrl-C quits (exit 130). Ctrl+A/Tab widens to every project on the machine, Ctrl+W to every checkout of the current repo (fan-out plus the last-cwd union arm — see 5b), Ctrl+B narrows to the checkout of the current git branch, and Ctrl+T cycles the time window (20m → 1h → 1d → 1w → all → 20m). Sessions are grouped by harness, the harness groups ordered by which harness was last opened from the picker (sticky, most-recently-used first, stored in the main clone's .wtft/config.json) — browsing never changes that order, only opening a session does. A window with no candidates says so and names Ctrl+T, rather than widening itself.
  • No Interactive Terminal (Pipes/Claude Code '!'): If standard input is NOT a TTY, OR standard input is a TTY but the picker's own output stream is not (wtft --tokens | less -R keeps stdin on the terminal while stdout is a pipe; wtft --json 2>/dev/null is the same shape for the stream --json draws to), WTFT selects ONLY an explicit -s path (existing, or a pending .jsonl) or a -s <substring> that matches exactly one session; with no -s it always exits 10, even when one session is in view. Otherwise it exits 10 (EXIT_SESSION_AMBIGUOUS), naming every candidate on stderr and nothing on stdout — this replaced the old behaviour of silently defaulting to the newest session.

5b. Which Claude Sessions Count As "Here" (a union, never a replacement) — and which scope key reaches it: The project-dir slug is a cache of where a session began, so matching on it alone loses sessions in three separate ways — but the picker's DEFAULT scope only ever uses the first of them; the other two are reachable by keypress, not automatic. (1) Physical slug — the directory name equals an encoding of a target directory. Two encodings are accepted, not one: Claude Code munges . to - as well as /, so ~/repo/.claude/worktrees/x is filed as …-repo--claude-worktrees-x; what it does to _ is unverified, so both hypotheses are matched (#144). This is the ONLY arm the default ("worktree") scope runs. (2) Recorded last cwd — the transcript's own tail says it was last written from a target, which is how a session that moved is still found where it now lives (#156). Runs only under Ctrl+W's "worktrees" scope, and only within the active time window — the arm's cost is bounded by whatever window the human is already looking through, and reaches its old unbounded cost only if Ctrl+T is cycled all the way to "all". (3) Worktree fan-out — "here" is every checkout of the current repo (git worktree list: main clone plus every worktree), symmetric in both directions, so a session recorded in a sibling worktree is listed from the clone and vice versa. Outside a git repo there is no fan-out, so --dir ~ does not list the whole machine (#145). Also Ctrl+W only. Ctrl+A/"all" scope skips folder matching entirely — every session for the harness, bounded only by the time window. Ctrl+B/"branch" scope narrows arm 3's fan-out to the single checkout matching the current git branch. Pi discovery shares arm 1 too (both encodings accepted): for the single-directory scopes ("worktree", "branch") it is an EXACT match against the wrapped --<slug>-- directory name, and only "worktrees"' fan-out uses containment, the same way Claude Code's slug-prefix fallback does. Pi also wires up arm 2 under Ctrl+W, and it is mostly inert there: Pi records cwd once, on its session_start entry, so the tail scan only resolves a DIFFERENT cwd than the physical slug already gives when the session moved directories after that entry — the ordinary case (never moved) makes the arm redundant with arm 1, not a null read; a transcript under roughly 512 KB has its whole file read by the widening scan and does resolve session_start's cwd. That is deliberate rather than a gap — the day Pi records a per-entry cwd, the arm starts catching an in-session move with no code change.

A fourth arm existed and was deleted (#89's first phase). When a session's last cwd named a directory that no longer exists, the whole transcript used to be read and every directory it had ever occupied matched against the target (#164) — and such a session rendered under the most recent directory that still existed, rather than naming one you cannot visit. Measured 2026-09-16 over 7,287 transcripts / 2.51 GB, that arm performed 6,952 whole-file reads per launch and returned 0 candidates the physical-slug arm had not: a transcript is filed under the directory its session started in, and a session usually starts in the main clone before entering a worktree, so arms 1 and 3 already reach it. It is the one place this union has ever narrowed. The shape it alone could reach — a session that started inside a worktree that has since been removed — is no longer listed, and renders under the slug it is filed under. resolveCwdHistory(), pickLiveCwd() and pathExists() no longer exist; the relocation records are still in the transcripts and nothing reads them. #89's SECOND phase (this one) is what scoped arms 2 and 3 behind keypresses instead of running them on every launch.

Settings Persistence (Cross-Harness Config)

All WTFT settings are persisted in harness-agnostic JSON config files via the shared extensions/lib/config.ts module. There is no .jsonl persistence — settings survive across Pi sessions, Claude Code invocations, and machine restarts.

Config Hierarchy (lowest → highest precedence)

  1. Code defaults — hardcoded (interval=1h, limit=10, mode=cumulative, showTicks=true, timezone=America/Los_Angeles, disabledEmoji=false).
  2. User-global config: ~/.config/princess-pi/wtft.json
  3. Project-local config: ./.princess-pi/wtft.json (overrides global keys)
  4. CLI flags — highest precedence, applied by caller after reading config.

Each level overrides only the keys it defines; missing keys inherit from the layer below. When settings are changed via /wtft in Pi, they are written to the project-local config if it already exists, otherwise to the user-global config.

Config Format (wtft.json)

{
  "interval": "1h",
  "limit": 10,
  "mode": "cumulative",
  "showTicks": true,
  "timezone": "America/Los_Angeles",
  "disabledEmoji": false
}

Widget Auto-Show

The WTFT widget auto-shows on session start if a config file exists (user has configured wtft at least once). No separate visible setting needed — delete the config file to permanently hide, or use /wtft --hide to hide for the current session only.

Log Parser Daemon Health Monitoring

The widget title line shows a colored status indicator for the background daemon:

  • ● reading... — CLI startup placeholder, shown before the first health check completes (500ms)
  • ● live — daemon is running and processing new interactions
  • ● idle (3:22 to expire) — no new data for 2m2s; countdown shows time until model cache expires (Claude: 5 min, DeepSeek: 1 hr, local: no countdown)
  • ● idle (cache emptied) — cache TTL fully elapsed (remaining ≤ 0 min); model context cache has expired
  • ● idle (local model) — daemon idle, no remote cache (local model)
  • ● stopped HH:MM — daemon exited (24h idle timeout or crash)
  • ● restarting... — daemon is being restarted

Status rendering is shared via renderDaemonStatus() in wtft-daemon-lib.ts — DRY between Pi widget and CLI watch modes.

Health Check Mechanism

The daemon health check (checkDaemonHealth) reads the PID file and the last ~8KB of the tag file to determine state:

  • PID alive + classified entries present → live
  • PID alive + only heartbeats for ≥ 2m2s → idle. The heartbeat's first timestamp (set by the daemon at idle start) is used as the clock baseline, so the countdown ticks accurately even across health-check poll intervals.
  • PID alive + fresh heartbeat but session mtime ≥ 2m2s → idle immediately. This handles daemon restarts on already-idle sessions — the startup heartbeat's freshness is overridden by the session file's modification time.
  • PID dead → stopped, with the most recent heartbeat's stop reason and timestamp.
  • PID dead but tag file written within 2s → state unchanged (debounce). Masks the restart gap when a new daemon replaces an old one, preventing a spurious "stopped" flash.

Provisional Reads (#443)

A one-shot wtft spawns the daemon and reads the tag file on the next statement, so on a session the daemon is about to repair, the read races the daemon it just started — and loses. On the measured specimen that was $79.74 against a true $84.59, a 5.7% undercount printed exactly like a settled total.

The daemon now appends a _meta.swept marker once its first sub-agent sweep completes. Its absence means no sub-agent transcript has been read since the tag was written. A read is provisional when either holds:

  • stale-version — the resolved tag is not at the current tagger version, so its numbers are at superseded semantics
  • unswept — a current-version tag holding classified data but no _meta.swept

When provisional, wtft still prints the total in full, adds a PROVISIONAL warning naming the reason, and exits 9 instead of 0. It does not block: waiting for a repair whose length scales with the session's sub-agent volume is the cost that read-then-render exists to avoid. Withholding the number would be worse than the undercount — it is usually close, and always better than nothing.

Exit 9 is distinct from 1 on purpose: the run failed and the run succeeded but the number is not final are different facts. It carries one bit, and --json carries the reason as provisional.reason (spec-26).

Update Timing

Status updates are triggered by three mechanisms, from fastest to slowest:

TriggerLatencyApplies to
Inotify (fs.watch) on tag file~667ms (daemon write interval)CLI --watch
Pi widget render timer~2-5s (widget refresh)Pi widget
60-second backup timer≤ 60sCLI --watch (fallback if inotify misses)
Initial startup500msCLI --watch

Inotify-driven updates mean that idle → live transitions are instant — the status flips the moment the daemon writes classified entries to the tag file. The 60-second timer is a safety net, not the primary mechanism.

The log parser daemon wraps its main poll loop in a try/catch so transient errors (disk full, permission denied, corrupted JSON) are logged and the daemon continues running on the next poll cycle — it does not crash silently.

Width is always auto-detected from terminal (clamped at 1023). No -w/--width flag. Watch modes re-render on terminal resize (SIGWINCH).

In CLI --watch mode, press r to restart the daemon. A per-session daemon is stopped and started again; a harness daemon, which serves every session readers have asked for under its root, is left running and asked to serve this session next (#248). The footer shows 'r' to restart in red when the daemon is stopped. The Pi widget auto-spawns a daemon on session start to keep the tag file warm for CLI use.

Management commands: --list (list running parsers), --cleanup (kill stale parsers), --restart (restart all), --stop <session> (stop one).
