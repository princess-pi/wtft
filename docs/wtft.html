Overview

The WTFT (Where The F***ing Tokens?!) utility provides visual, granular accounting of your session's token consumption and associated monetary cost ($ USD). It reads the active session's append-only .jsonl log, classifies each interaction into one of 14 categories, groups the interactions into bins by time or by turn count (the -i interval), and draws a colour-coded terminal bar chart, one row per bin: a running total by default, or each bin's own spend under --bucket. The chart itself, drawn by its own code, is the chart spec (served at https://wtft-artifacts.princess-pi.dev/).

/wtft -o, --other

Outputs a cleanly aligned, descending-frequency histogram of the primary executable/command names (e.g., node, npm, cat, mkdir), their execution counts, and cumulative costs during turns classified as "Other". Under the Pi TUI Widget, this prints the histogram directly into the prompt-response message scroll (via chat notification) without modifying the chart widget. wtft [options] (Standalone Shell Binary — Cross-Harness)

Run the cost auditor directly from your host shell outside of Pi. Just like bin/merge.mjs, it is shipped as plain ESM JavaScript (bin/wtft.mjs) so it runs on stock node without triggering Node's type-stripping errors. Install it with bin/install-wtft, which builds, then puts four entries in ~/bin: the bundles wtft.mjs and wtft-daemon.mjs as copies, plus wtft and wtft-daemon as symlinks to them (spec-46). The old line here named npm install -g github:duppypro/princess-pi-packages, which is wrong three times over: that repo was renamed to princess-pi-tools, wtft was extracted out of it, and nothing is on npm (#29). You can invoke it as wtft, via the ./wtft wrapper from the repo root, or through Claude Code's ! prefix (e.g. !wtft -i 1d). It reuses the exact same classification engine as the Pi extension, but outputs directly to stdout, allowing you to pipe the output (e.g., wtft | less -R).

Classification Taxonomy & Priority Rules

Each interaction gets one of 14 categories: plan, spec, research, web, grep, code, tests, git, agents, prompt, compaction, interrupted, overhead and other. classifyInteraction (extensions/lib/wtft-parser.ts) walks a ladder, and the first rung with an answer wins: the category a tag line already carries, then an interrupted turn (interrupted), then the paths of the files read or written, then tool names, then the shell commands that actually ran, then a reply with text and no unrecognized tool (prompt), else other. overhead and compaction are not rungs: they are the slice of a turn's cost that splitOverheadCost cuts off. The ladder, the path rules and the command families: parser spec, § How a turn gets its category.

The chart's legend labels are the category names capitalized, except compaction → Cmpct, interrupted → Waste and overhead → Ovrhd. Each category's colour, label and legend position come from CATEGORY_STYLE and CATEGORY_ORDER in extensions/lib/wtft-renderer.ts; the chart spec shows them drawn.

SURGE Timeline (24-hour pricing bar)

The title line renders a 24-hour timeline of the model card's surge schedule, when it has one. Orange segments mark surge-priced hours, green segments mark normal-priced hours. The schedule is the model card's surge field. DeepSeek's four cards share one, weekday-gated by DEEPSEEK_WEEKEND_OFFPEAK_FROM (#495); the hours themselves are not re-typed here — the Model Pricing section below renders them from the generated manifest. The bar marks an hour when any minute of it bills above 1, by asking getPeakMultiplier. It paints the schedule for the day containing now, while the bins beneath it may be older — on a weekend the DeepSeek bar shows no surge hours even where weekday bins are still flagged. The timeline uses ─ box-drawing horizontal rule characters (U+2500) for a continuous unbroken line.

Markers: The current hour displays a clock-face emoji (🕐–🕛, hour % 12) — including the noon hour (🕛 at 12:00p–12:59p). Solar noon is a separate ☀️ glyph between hour 11 and hour 12, so every hour keeps its own slot: 12 hour-slots left of the sun, 12 right (#7). The timeline is bookended by the moon at local midnight where the strip starts and the moon at the next local midnight (🌑–🌘, from the synodic-month formula anchored to the 2026-07-14 new moon, with half-phase centering). Those two phases can differ. Noon is the sun, passed in as its own glyph.

Badges: When the card has a schedule and the instant is in or near a window, a badge is appended. The active badge prints that card's multiplier (⚡ SURGE 2x for DeepSeek). ⚡ SURGE APPROACHING is the SURGE_APPROACH_MINUTES before the window opens, and ⚡ SURGE ENDING is the SURGE_ENDING_MINUTES before billing drops to 1. That instant follows windows that touch or overlap, including one that starts at 0 on the next UTC day when this one ends at 1440, and a weekend cutoff that falls inside the run. Under --no-emoji the bolt is !!, the moons are |, the sun is * and the clock face is @.

Cache Miss divider: When a parent turn re-primes its prefix instead of reading it — cache_read_input_tokens 0 with cache_creation_input_tokens above 0, or a recache the overhead split finds, where only a small prefix stayed cached (#241) — a ── Cache Miss ── divider line with tick-position ┼ markers is drawn directly below that bin's row (rows are newest-first, so it separates the missed turn from the older turns whose cache it could not reuse) — always shown, in turn-based intervals as well as time-based ones.

This is observed, not predicted. Until #152 the divider was inferred from elapsed time against the 5m/1h TTL and was labelled Cache Expired; that model could not see invalidation which consumed no time — a model switch, a system-prompt edit — and was disabled entirely for turn-based intervals (#121). The label says "Miss" rather than "Expired" because the usage block proves the re-prime happened but says nothing about why, and TTL is only one of the causes.

The flag is computed before the tag is written (Interaction.cacheMiss, tag field miss, introduced at tagger v2.7.0): the zero-read case at parse time, the recache case where the overhead split runs, since it needs the previous turn's context. Not at render time, because the compaction/recache meter-split writes cr and cw onto two separate tag lines, so the original pair is gone from the tag, and the recache case also needs the previous turn's context. A session's first turn is marked when it reads no cache at all. One that finds a small shared prefix already cached is not, because the recache rule needs a previous turn to compare against. Since tagger v2.11.0 a partial re-prime, where a small prefix survives, is marked too, by the overhead split's own recache rule (spec-241).

Sidechains are not marked (#115, gated from tagger v2.8.1). A Task subagent starts with an empty context, so read-0 / write-everything is how it begins rather than something it lost, and flagging it made the divider noise that grew with fan-out. The divider is parent-only, matching the exclusion splitOverheadCost already applies to recache detection. It is gated twice, because the two harnesses mark a subagent differently: Claude Code stamps isSidechain on every turn of a subagent transcript, which the parse-time rule reads, while Pi marks one at file level with a parentSession header and no per-entry flag — so the flag is cleared again from provenance, for anything that came out of a subagent transcript at all. That clear is one exported seam, clearSubagentCacheMiss, called from two readers that must stay in step — loadSubagentInteractions (the CLI and Pi widget read path) and the session tagger's syncSubagentTranscript (extensions/lib/session-tagger.ts, which produces the tag lines the CLI renders from). Clearing it in only one bakes miss: 1 into the tag file and makes the two disagree about the same session. No isSidechain field was added to the tag wire format; the gate runs before the tag line is written. The recache case (#241) is decided while the session's own lines are serialized, and subagent lines never pass through that split.

Unified in buildWtftLines: Both Pi widget and CLI (non-watch and --watch) share one code path: chartLines (spec-389) calls buildWtftLines, which calls renderWtftChart, which draws the strip. The Pi widget passes the session's current model. The CLI and --watch leave the model unset, so the strip uses the first classified interaction that names one. The strip follows that card's surge field. A card with no surge schedule renders an all-green timeline with no badges.

TUI Visualization Style

The chart spec is the live spec for everything in this section: its four presets are drawn by the chart's own code, and its chart picker (picker.html) draws any combination of flags. This section names the parts; the cell rules, rounding and widths are there, not here.

Two modes, -c/--cumulative (the default) and -b/--bucket, times two units, --cost (the default) and --tokens, give four bars. A drawn cell is one category, and its colour is that category's.

  • Cumulative Mode (running total, stacked): each bin's bar is the running total up to and including that bin: cost under --cost, tokens under --tokens, stacked by category in legend order. Each category's segment draws █ for its earlier bins, then ✨ on a dark shade of its colour for its share that is new this bin, to within a cell or two (* in each of those cells under --no-emoji). A key line follows the rows: █ earlier bins ✨ this bin, with ** for ✨ under --no-emoji. On the cost bar a category's segment holds at least its cells on the next-older displayed row (#106), unless the trim step that keeps the bar at its width takes one back (chart spec § Rows); the token bar has no such clamp.
  • Bucket Mode (this bin only): the cost bar is a scatter: each category with cost in the bin puts one █ at the column for its own cost. When two categories land on the same column, the cell goes to the larger cost, and a tie keeps the earlier category in legend order. The token bar is a █ stack. A bucket bar draws no ✨ and prints no glyph key.

A token bar, in either mode, draws one $ when the bin's web cost is above 0, its web tokens are 0 and the bar has a free cell, and a $ = cost-only (web tools) note follows the rows.

Every row prints the bin label, then four numbers before the bar, in this order: incremental cost (+$), total latest cost ($), incremental tokens (+1.5k), and total latest tokens (3.0k tok). --cost and --tokens choose the bar, not those numbers. --tokens also prints the per-model summary and can persist the unit. --no-cost hides the two cost numbers and --no-tokens hides the two token numbers. On the Pi widget a hide lasts for the rest of the process, and passing the flag again keeps that pair hidden. The CLI hides for that run only. When the time label and these numbers take more than 25% of the width, they are compacted one step at a time, stopping at the first step that brings them to 25% or less; after the fifth nothing more is removed: single spacing, whole units for $1 and 1k and over, no + on the deltas, no $ on the cost delta, and 12k tok written 12kt (spec-362), so at 80 columns a row reads 22:42 13 $23 4k 12kt. After that, when the bar would still be under 15 cells, the token numbers drop first, then the cost numbers. A bin holding a surge-priced turn draws its label and numbers in bold orange, and the bar keeps its category colours; while the columns have their full two-space gap, a ⚡ (!! under --no-emoji) fills the gap after the first number column, or after the label when at most one column shows.

The legend is the second line, under the title, with no 'Legend:' prefix: every category, in legend order, each a coloured █ followed by its label.

The third line is the scale, in grey: ── Mmm-DD with the newest bin's date, run out with ─ to where the bar starts, then the rule across the bar with five reverse-video labels embedded in it, at 0, ¼, ½, ¾ and full scale (dollars for a cost bar, tokens for a token bar). A label that would overlap an earlier one is dropped, and the line is drawn only when the scale is above 0 and the bar is at least 15 cells. The date-change and Cache Miss lines between rows have the same ── label ─… shape in the same grey, with a ┼ at each of the five scale ticks.

Architectural Design

1. Log parser daemon: wtft-daemon classifies each interaction and writes pre-computed entries to a harness-agnostic tag file (wtft-tags/<session>.wtft-tag.v<WTFT_TAGGER_VERSION>.jsonl). A session under the Claude projects root or the Pi sessions root is served by that root's one process. A session outside those roots keeps its own process. Costs are rounded to 6 decimal places (micro-cent precision) before serialization to eliminate float drift between the widget's in-memory subagent parse and the file-based CLI. In Pi, the widget reads the session's own turns from the tag file (readTagFileWithVerdict, since #176), the same file the CLI reads, and spawns a daemon on session_start to keep it warm. After WTFT_DAEMON_IDLE_MS (24h) with no activity (a new turn, a subagent record written, or a poll of a session not yet written), a per-session process exits, and the Pi agent_end handler checks health via health and starts one again. A harness daemon stays up and drops that session with its lease; while that harness runs, the next write to its own transcript, or the next request, adopts it again. A session dropped for idling is forgotten 24h after it was dropped unless written first, or within a minute of its transcript being deleted, and a harness daemon left with nothing to serve or watch for 24h after that stops. One whose root is removed stops too, handing the sessions it served, was retrying and had dropped for idling to the next harness a reader starts; until then a write adopts nothing. A harness daemon reads only the sessions a reader asked for, and what they spawned. When it adopts a session, it flushes that session's own turns before reading its subagents, so a report shows that sum at once, marked provisional until the subagents are in. On a version bump the old daemon is replaced with no manual restart: a per-session daemon when the new one finds the old-version tag file, a harness daemon when a start from a newer tagger finds it holding the root.

2. Binning Engine: getBinInfo puts each interaction in a bin from the -i interval: by its timestamp for a time interval (m, h, d, w, e.g. 6m or 1d), or by turn count for a turn interval (t, e.g. 5t).

3. Scaling & Layout: The bar gets the width left after the label area and the scale's reserved cells. Its scale is the whole session's total in cumulative mode, and the largest displayed bin in bucket mode, rounded up. How many cells each category gets: chart spec, § Rows.

4. Recursive Subagent Rollup: When a Claude Code session log is targeted, WTFT auto-detects if a subagent directory exists (e.g., <session-id>/subagents/). If present, WTFT recursively reads all subagent .jsonl logs and blends their interactions chronologically based on their individual timestamps. This guarantees that binned timelines and other command histograms represent the true, cumulative cost and work allocations of the entire multi-agent session tree.

5. The Scoped Session Picker (#89): When running WTFT without an explicit session path option, WTFT discovers session logs SCOPED to the current directory by default — a folder-name match alone (any encoding, see 5b), no whole-repo scan, no cross-directory lookup — and to the last 20 minutes. That default is what makes a plain launch cost a handful of stat calls rather than a scan of every transcript on the machine (measured 2026-09-18: ~7 ms against the pre-#89 default's 2.0 s warm on an 11,005-transcript corpus). The selector display shortens the path to a compact form: ~/g-p/<project>/<date>...<uuid-tail> where g-p is the first-letter shortening of git-projects. The project name is kept in full, with one exception: a git worktree checkout compacts to <repo>/w/<branch> (so worktrees-demo-99-branch renders as demo/w/99-branch) — otherwise every worktree row reads as an unrelated project with a very long name. UUIDs are truncated to the last 4 hex characters. Session age is shown as a relative time (e.g. 2h ago, 3d ago).

  • Interactive Picker (TTY): If standard input AND the stream the picker draws to (stdout normally, stderr under --json) are both real terminals, WTFT renders the interactive picker — even under --json, drawn to stderr there so stdout stays one clean JSON document — showing the compact path, estimated cost, turn count, harness, and relative time. j/k/arrows navigate (wrapping the whole list, sliding an 11-row window past 12 candidates, with a "12-22 of 40" position line), Enter selects, q/Ctrl-C quits (exit 130). Ctrl+A/Tab widens to every project on the machine, Ctrl+W to every checkout of the current repo (fan-out plus the last-cwd union arm — see 5b), Ctrl+B narrows to the checkout of the current git branch, and Ctrl+T cycles the time window (20m → 1h → 1d → 1w → all → 20m). Sessions are grouped by harness, the harness groups ordered by which harness was last opened from the picker (sticky, most-recently-used first, stored in the main clone's .wtft/config.json) — browsing never changes that order, only opening a session does. A window with no candidates says so and names Ctrl+T, rather than widening itself.
  • No Interactive Terminal (Pipes/Claude Code '!'): If standard input is NOT a TTY, OR standard input is a TTY but the picker's own output stream is not (wtft --tokens | less -R keeps stdin on the terminal while stdout is a pipe; wtft --json 2>/dev/null is the same shape for the stream --json draws to), WTFT selects ONLY an explicit -s path (existing, or a pending .jsonl) or a -s <substring> that matches exactly one session; with no -s it always exits 10, even when one session is in view. Otherwise it exits 10 (EXIT_SESSION_AMBIGUOUS), naming every candidate on stderr and nothing on stdout — this replaced the old behaviour of silently defaulting to the newest session.

5b. Which Claude Sessions Count As "Here" (a union, never a replacement) — and which scope key reaches it: The project-dir slug is a cache of where a session began, so matching on it alone loses sessions in three separate ways — but the picker's DEFAULT scope only ever uses the first of them; the other two are reachable by keypress, not automatic. (1) Physical slug — the directory name equals an encoding of a target directory. Two encodings are accepted, not one: Claude Code munges . to - as well as /, so ~/repo/.claude/worktrees/x is filed as …-repo--claude-worktrees-x; what it does to _ is unverified, so both hypotheses are matched (#144). This is the ONLY arm the default ("worktree") scope runs. (2) Recorded last cwd — the transcript's own tail says it was last written from a target, which is how a session that moved is still found where it now lives (#156). Runs only under Ctrl+W's "worktrees" scope, and only within the active time window — the arm's cost is bounded by whatever window the human is already looking through, and reaches its old unbounded cost only if Ctrl+T is cycled all the way to "all". (3) Worktree fan-out — "here" is every checkout of the current repo (git worktree list: main clone plus every worktree), symmetric in both directions, so a session recorded in a sibling worktree is listed from the clone and vice versa. Outside a git repo there is no fan-out, so --dir ~ does not list the whole machine (#145). Also Ctrl+W only. Ctrl+A/"all" scope skips folder matching entirely — every session for the harness, bounded only by the time window. Ctrl+B/"branch" scope narrows arm 3's fan-out to the single checkout matching the current git branch. Pi discovery shares arm 1 too (both encodings accepted): for the single-directory scopes ("worktree", "branch") it is an EXACT match against the wrapped --<slug>-- directory name, and only "worktrees"' fan-out uses containment, the same way Claude Code's slug-prefix fallback does. Pi also wires up arm 2 under Ctrl+W, and it is mostly inert there: Pi records cwd once, on its session_start entry, so the tail scan only resolves a DIFFERENT cwd than the physical slug already gives when the session moved directories after that entry — the ordinary case (never moved) makes the arm redundant with arm 1, not a null read; a transcript under roughly 512 KB has its whole file read by the widening scan and does resolve session_start's cwd. That is deliberate rather than a gap — the day Pi records a per-entry cwd, the arm starts catching an in-session move with no code change.

A fourth arm existed and was deleted (#89's first phase). When a session's last cwd named a directory that no longer exists, the whole transcript used to be read and every directory it had ever occupied matched against the target (#164) — and such a session rendered under the most recent directory that still existed, rather than naming one you cannot visit. Measured 2026-09-16 over 7,287 transcripts / 2.51 GB, that arm performed 6,952 whole-file reads per launch and returned 0 candidates the physical-slug arm had not: a transcript is filed under the directory its session started in, and a session usually starts in the main clone before entering a worktree, so arms 1 and 3 already reach it. It is the one place this union has ever narrowed. The shape it alone could reach — a session that started inside a worktree that has since been removed — is no longer listed, and renders under the slug it is filed under. resolveCwdHistory(), pickLiveCwd() and pathExists() no longer exist; the relocation records are still in the transcripts and nothing reads them. #89's SECOND phase (this one) is what scoped arms 2 and 3 behind keypresses instead of running them on every launch.

Settings Persistence (Cross-Harness Config)

WTFT settings are persisted in harness-agnostic JSON config files via @princess-pi/libs/config, so they survive across Pi sessions, Claude Code invocations, and machine restarts. The one .jsonl layer is a session log's wtft-settings and emoji-settings entries, which only --watch reads.

Config Hierarchy (lowest → highest precedence)

  1. Code defaults — hardcoded (interval=1h, limit=10 in the Pi widget and 17 in the CLI, mode=cumulative, timezone=America/Los_Angeles in the Pi widget and the system's local zone in the CLI, disabledEmoji=false).
  2. User-global config: ~/.config/wtft/config.json ($XDG_CONFIG_HOME/wtft)
  3. Project-local config: .wtft/config.json (overrides global keys)
  4. Session log, --watch only: a wtft-settings entry in the session .jsonl overrides the config's interval, limit, mode and timezone, and an emoji-settings entry its disabledEmoji.
  5. CLI flags — highest precedence, applied by caller after reading config.

Each level overrides only the keys it defines; missing keys inherit from the layer below. When settings are changed via /wtft in Pi, they are written to the project-local config if it already exists, otherwise to the user-global config.

Config Format (config.json)

{
  "interval": "1h",
  "limit": 10,
  "mode": "cumulative",
  "timezone": "America/Los_Angeles",
  "disabledEmoji": false
}

Widget Auto-Show

The WTFT widget auto-shows on session start if a config file exists (user has configured wtft at least once). No separate visible setting needed — delete the config file to permanently hide, or use /wtft --hide to hide it for the rest of the Pi session, until the next /wtft.

Health Check Mechanism

The CLI's startup wait and --list's RUNNING/DEAD apply its liveness rule directly. The rule, the reason codes and the readers: spec-daemon-health, the module's live spec.

Provisional Reads (#443)

A one-shot wtft spawns the daemon and reads the tag file on the next statement, so on a session the daemon is about to repair, the read races the daemon it just started — and loses. On the measured specimen that was $79.74 against a true $84.59, a 5.7% undercount printed exactly like a settled total.

The daemon appends a _meta.swept marker after a sub-agent sweep that read every sub-agent transcript cleanly and holds no turn back, when the tag grew since the last marker (always on the first such sweep after the daemon starts serving the session) or an unswept marker is pending. A data or unknown line, or an {"_meta":{"unswept":…}} marker (written when the session's own transcript fails to read, and on resuming an earlier tag), after the last swept marker means the sub-agents have not all been read into the tag since. A sub-agent that fails to read writes no marker; it only withholds swept. The format: wtft-tag-format.md §2f. A read is provisional when either holds:

  • stale-version — the resolved tag is not at the current tagger version, so its numbers are at superseded semantics
  • unswept — a current-version tag holding data with no _meta.swept after its last data or unknown line or unswept marker

When provisional, wtft still prints the total in full, adds a PROVISIONAL warning naming the reason, and exits 9 instead of 0. It does not block: waiting for a repair whose length scales with the session's sub-agent volume is the cost that read-then-render exists to avoid. Withholding the number would be worse than the undercount — it is usually close, and always better than nothing.

Exit 9 is distinct from 1 on purpose: the run failed and the run succeeded but the number is not final are different facts. It carries one bit, and --json carries the reason as provisional.reason (spec-26).

Update Timing

Status updates are triggered by these mechanisms:

TriggerLatencyApplies to
Inotify (fs.watch) on tag file~667ms (daemon write interval)CLI --watch
Pi widget refresh: a 60 s timer, and Pi's agent_settled and session_tree events≤ 60sPi widget
Watchdog1,334 msCLI --watch, while it does not read the daemon as dead
Initial startup500 ms after the tag file appearsCLI --watch

Inotify-driven updates mean that idle → live transitions are instant — the status flips the moment the daemon writes classified entries to the tag file. The watchdog is a safety net, not the primary mechanism.

The log parser daemon wraps its main poll loop in a try/catch: a transcript it cannot open, stat, hash, attribute or serialise marks the poll failed, so the tag stays provisional, and the next poll retries, with one WARNING line per transcript on stderr (a corrupted JSON line is skipped silently; the poll loop's own error line is printed only under WTFT_DAEMON_DEBUG). A failed write to the tag file (disk full, permission denied), and a tag the daemon cannot read or truncate when it starts, is fatal on purpose: fatalTagMutation marks the lease rebuild, prints the failure and exits 1, so the next wtft rederives the tag rather than trusting a partial one.

When a daemon stops serving a session it appends a stop line, {"_hb":"stop","reason":"<why>"}: the reason (SIGTERM, idle timeout, session removed, harness root removed, …) says why the session is no longer served. None is written by a per-session daemon that lost its lease, by a harness dropping a session whose lease went elsewhere (a wtft --stop of a harness session among them), on a failed tag write or a tag it cannot read or truncate at start, or when the tag file does not exist. Which daemons write it: wtft-tag-format.md §2c.

In the CLI and --watch, width comes from the terminal less --pad on each side, capped at 1023; the CLI reads -w/--width and ignores it, which only the Pi widget honours. Watch modes re-render on terminal resize (SIGWINCH).

In CLI --watch mode, press r to restart the daemon. The lease holder is stopped and a new daemon started once it has exited, while the view keeps running; a holder that outlives the stop, or one it may not signal, is left running and shows restart failed. Which holders it may stop, and how: spec-holder §2 and §3. A harness daemon, which serves every session readers have asked for under its root, is left running and asked to serve this session next (#248). The footer shows 'r' to restart in red when the daemon is stopped; the hint appears only when the CLI passes the daemon path, which wtft --watch always does. The Pi widget auto-spawns a daemon on session start to keep the tag file warm for CLI use.
