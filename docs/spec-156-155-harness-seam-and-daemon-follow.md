# Spec — Hard harness seam + cwd-aware discovery (#156), daemon follows a moved session (#155)

Two issues, one branch, in this order. #156 builds the primitive — *resolve a session by id
across project dirs* — that #155's live-follow fix consumes. Building it once is the reason
they are bundled.

---

# #156 — Discovery is cwd-slug-only, and the harness code has no seam

## Part 1 — Discovery is a cache of where a session *began*

`extensions/lib/session-selector.ts:64-71` builds exactly one Claude project slug, from cwd:

```ts
const cwdSlug = resolvedCwd.replace(/[/\\]/g, "-");
const sessionsSubdir = path.join(claudeProjectsDir, cwdSlug, "sessions");
const directDir = path.join(claudeProjectsDir, cwdSlug);
```

The slug is assigned when a session starts and never revised. Nothing in `~/.claude/projects/`
indexes across dirs. So a session that moved — into a worktree, or by an ordinary `cd` into a
subdirectory — is unreachable from where it now lives.

### Measurement

`research/156-cwd-resolution-probe.mjs`, over every Claude transcript on this machine:

```
files=40  resolved=40  mismatched=1  read=0.5MB  elapsed=11ms
  MISMATCH 19d0ba8d  dir=-home-princess-pi-git-projects-rogue-savvy  cwd=/home/princess-pi/git-projects/rogue-savvy/frontend
```

Every transcript carries its own answer. Walking backwards from the tail to the first entry
with a `cwd` resolves 40/40 at **11 ms total**, reading **0.5 MB** of 64 MB — cheap enough to
run on every selector invocation, so no index and no cooperating writer is needed. (A pointer
file would only be written if a parser happened to be running at the moment of the switch,
which cannot be guaranteed.)

The one live mismatch is not a worktree: it is a session filed under the repo-root slug whose
cwd is a subdirectory. The worktree case is the loud instance of a general defect.

### Rule — union, not replacement

A transcript is a candidate for target directory `D` when **either**

- its physical project-dir slug equals `slug(D)`, **or**
- its resolved last-cwd equals `D`.

Then dedup by session id, keeping the newest mtime.

Union is the whole point. A pure last-cwd match would *change* existing behaviour — the
`rogue-savvy` session above would stop appearing at the repo root, where it appears today.
Union is strictly additive: it never drops a session the current code finds.

### Tail-scan refinements

- Start at **8 KB**, widen to 64 KB then 512 KB only when no `cwd` is found; scan the whole
  file as a last resort. (0.5 MB read at 8 KB vs 2.3 MB at a fixed 64 KB — the issue's
  prototype used the fixed window.)
- When the read did not start at byte 0, **drop the first line** — it is a truncated fragment.
- Memoise on `(path, mtimeMs, size)`. An unchanged transcript is never re-read.

### Pi is unaffected, deliberately

Pi records `cwd` once, on the `session_start` entry — not per entry. A tail scan of a Pi
transcript finds nothing and contributes nothing to the union, leaving Pi discovery exactly as
it is today. That is correct rather than a gap: Pi's directory slug already encodes the start
cwd, and Pi has no worktree-switch mechanism that rewrites it. The resolver is wired into Pi
discovery anyway, so the day Pi starts recording per-entry cwd, it works with no code change.

## Part 2 — Hard harness seam

### What is entangled today

| File | Entanglement |
|---|---|
| `session-selector.ts` | `walk()` takes `type: "pi" \| "claude-code"` and branches inline on it; both directory layouts handled in one function |
| `wtft-parser.ts:149-150` | `isPiSchema` / `isClaudeSchema` in one function body, plus field-level fallbacks (`usage.input_tokens ?? usage.input ?? 0`) that quietly encode "either harness might have written this" |
| `wtft-parser.ts:418-447` **and** `bin/wtft-daemon.ts:327-357` | Stream-control markers (`thinking_level_change`, `model_change`, `compaction`, `isCompactSummary`, interrupt) hard-coded **twice**, once per parse path |

The renderer seam, by contrast, already holds: `wtft-renderer.ts` consumes `Interaction`s and
tag lines and knows nothing about harnesses. That is the shape to extend.

### Target shape

```
extensions/lib/harness/
  types.ts               — the interfaces every harness implements
  registry.ts            — enumerates harnesses from runtime config
  session-cwd.ts         — shared memoised tail-scan cwd resolver
  builtins.generated.ts  — ⚠️ GENERATED by build.ts (static import table)
  claude-code/discovery.ts
  claude-code/parse.ts
  pi/discovery.ts
  pi/parse.ts
```

Directory name **is** the harness id, so `claude-code/` and `pi/` keep the ids already carried
on `SessionCandidate.harness`.

### The two interfaces

**Discovery** — where do this harness's transcripts live?

```ts
interface HarnessDiscovery {
  readonly id: string;
  readonly label: string;                                  // selector column, e.g. "Claude"
  discover(targetCwd: string | null): SessionCandidate[];  // null = no cwd filter
  resolveSessionById(sessionId: string): string | null;    // the primitive #155 needs
}
```

**Parse** — schema knowledge, and nothing else.

```ts
interface HarnessParseAdapter {
  readonly id: string;
  matchAssistant(entry: any): AssistantTurn | null;  // null = not this harness's assistant turn
  readBlock(block: any): ParsedBlock | null;         // one content block
  readControlEntry(entry: any): ControlSignal | null; // model_change, compaction, interrupt, …
}
```

`AssistantTurn` carries the fields whose *location* is schema-specific (message id, request id,
model, timestamp, sidechain flag) plus a `NormalizedUsage` in Anthropic-compat field names and
a `nativeCost` (Pi records a per-turn cost; Claude Code does not). `ParsedBlock` is
`{kind:"text"|"thinking"}` or `{kind:"tool", name, files, commands}` — the adapter maps its own
argument names (`args.path` vs `args.file_path`) to files and commands; shared code runs
`extractFilesFromBashCommand` and `mapToolToCategory` on the result.

Everything downstream stays harness-agnostic and unmoved: the `Interaction` type, cost
calculation, classification, the meter-split, dedup, tag serialization, the daemon loop, and
every renderer. **Renderers read only `wtft-tag` files**, which are the harness parsers'
output — that contract does not change and is what makes the seam hold.

### Why `parseEntryToInteraction` is not split in two

The two schemas differ in ~20 lines of field access inside a ~150-line body whose remainder —
cost resolution, cache-TTL/miss observation, server-tool billing, surge pricing, tool
classification — is identical and heavily tested. Copying that body per harness would move
the entanglement rather than remove it, and would put cost logic behind the seam where a new
harness could get it wrong. The adapter normalizes; the shared body computes. The seam sits
between *schema* and *semantics*, which is where the difference actually is.

**Road not taken:** one full parser per harness. It leads to per-harness cost drift and N
copies of `#52 Phase 3` to keep in step — the opposite of the deep-module shape.

### Registry: two channels, one contract

Config: `~/.config/princess-pi-packages/wtft-harnesses.json` (XDG respected), same precedent as
`wtft-pricing.json` — read at runtime, not baked at build.

```json
{
  "pi": { "enabled": false },
  "codex": {
    "label": "Codex",
    "discovery": "~/.config/princess-pi-packages/harness/codex/discovery.mjs",
    "parse":     "~/.config/princess-pi-packages/harness/codex/parse.mjs"
  }
}
```

- **In-repo channel.** `build.ts` scans `extensions/lib/harness/*/` and writes
  `builtins.generated.ts`, a static import table. Adding a harness = two new files + a config
  entry; the table regenerates. **No shared file is edited.** Static imports keep the bundle
  self-contained and behave identically under Bun's bundler and the Pi extension's tsx loader.
- **Out-of-tree channel.** A config entry with `discovery`/`parse` module paths is
  `await import()`ed at startup by `loadExternalHarnesses()` — no rebuild at all. `.mjs` only:
  stock node cannot import `.ts`, and requiring node ≥ 22.6 type-stripping from a global
  install was already ruled out (#31).

`loadExternalHarnesses()` is async and called once at startup (`bin/wtft.ts`,
`bin/wtft-daemon.ts`), exactly like `loadUserPricing()`. `getHarnesses()` stays **sync**, so
`discoverSessions()` and `parseEntryToInteraction()` keep their current signatures and the hot
parse path takes no async penalty.

### Acceptance criterion

`docs/adding-a-harness.md` — a guide whose steps are (1) add `harness/<id>/discovery.ts`,
(2) add `harness/<id>/parse.ts`, (3) add a config entry. Exercised against a real Codex sketch
committed under `research/156-codex-harness-sketch/`. If supporting Codex required touching
`wtft-renderer.ts`, `wtft-cost.ts`, `wtft-daemon-lib.ts`, or the selector's shared logic, the
seam is in the wrong place — the sketch is what proves it, not the assertion.

# #155 — A live daemon loses its file when the transcript moves

The premise correction in the issue body stands and is the starting point: the transcript is
**moved**, not copied. There is no duplication and no double-count. What remains is smaller and
real — a running parser watching a path that vanishes.

`bin/wtft-daemon.ts:937` and `:1022`:

```ts
if (!fs.existsSync(sessionPath)) { shutdown("session removed"); return; }
```

A worktree switch moves the transcript; the daemon sees its path vanish and exits. `--watch`
notices within ~1.3 s (`HEALTHY_BEAT_MS = 1334`) and reports the daemon dead.

## Change 1 — Distinguish moved from deleted

At both `shutdown("session removed")` branches, first re-resolve the session by id across
project dirs via the harness registry. Only shut down when it is genuinely gone. On a hit:
re-point `sessionPath`, log the move under `WTFT_DAEMON_DEBUG`, continue.

Incremental parsing survives untouched: `parseNewLines` keys off `lastSize`, and a move
preserves both inode and size — the next poll reads from exactly where it left off.

## Change 2 — Re-key the singleton on session identity, not path

```ts
const sessionHash = createHash("sha256").update(sessionPath).digest("hex").slice(0, 12);
```

After a move the hash changes, so a `wtft` run from the new directory would not recognise the
still-live daemon and would spawn a **second** one on the same transcript. Re-key on
`path.basename(sessionPath)` — the transcript filename, which is a UUID (Claude) or
`<timestamp>_<uuid>` (Pi), unique per session and invariant under a move between project dirs.

This is the change that makes "follow, don't fan out" safe. `getDaemonPidPath()` in
`wtft-daemon-lib.ts` and the daemon's own computation must agree — they already share the
formula; only the input changes.

**Road not taken:** inode-keyed identity. It is the most faithful notion of "same file", but it
is not derivable from a path the CLI holds before the file is opened, and it does not survive
the copy-then-delete form of a move. The basename is stable under both.

**Correction (#157):** the basename is stable under a move but is *not* unique — every file
named `session.jsonl` on the machine collapsed onto one lease. Both this key and the sibling
tag scan are now gated on the basename actually being a session id (a UUID, which every real
transcript carries); anything else keeps the pre-#155 full-path key. See
`docs/spec-157-session-identity-gate.md`.

## Change 3 — A moved daemon's tag file stays reachable

The daemon keeps writing to the tag path it opened at startup. That is what lets an attached
`--watch` survive: `fs.watch` is bound once to a fixed path in `watchTagFile` and never
re-resolves.

But a *new* `wtft` invoked from the new directory computes a tag path in the new dir and finds
nothing. So `getTagPath()` gains a cross-dir fallback, resolved in this order:

1. current-version tag in the session's **own** dir → use it;
2. current-version tag in a **sibling** project dir (matched on transcript basename) → use it;
3. any-version tag in the own dir (existing behaviour, newest mtime);
4. default (current-version path in the own dir).

Sibling ranks above stale-own-dir on purpose: that is precisely the case #155 measured — a
stale **v2.6.1, 125-line** tag in the main clone while the fuller **v2.7.0, 356-line** tag sat
in the worktree's project dir. The more complete artifact wins instead of being stranded.

Cost: on the miss path only, one readdir of `~/.claude/projects` (13 dirs here) plus each
`wtft-tags/`. Basenames are UUIDs, so a cross-dir basename match cannot collide.

**Orphan sweeping declined.** #155 offers "delete tag files whose sibling transcript is absent
from that dir". With the fallback above those files stop being dead weight — they are found and
used. Deleting them would throw away the *more complete* of the two artifacts, which is the
opposite of the measured problem. Left in place.

## Change 4 — Do not reap a daemon that merely moved

`reapAndWarn()` (`bin/wtft-daemon.ts:463`) and `--cleanup` both read `--session` from
`/proc/<pid>/cmdline` and **SIGTERM any daemon whose session path no longer exists**. After a
move the cmdline still shows the old path, so every `wtft` run would kill the very daemon this
issue is about keeping alive. Both call sites gain the same re-resolve-before-kill guard.

This coupling is the reason changes 1 and 4 must land together: fixing the poll loop alone
would leave the daemon to be shot from outside.

# As built — reconciliation

Everything below is how the shipped code differs from, or adds to, the design above. Recorded
after the tests ran, per Step 5.

## Additions the design implied but did not name

**`ParsedBlock.handled`.** A tool block carries an explicit `handled` flag rather than letting
shared code infer "recognized" from empty `files`/`commands`. Without it, a `Read` call with no
path argument would have fallen through to category mapping and been marked
`unrecognizedTool` — a behaviour change the pre-seam code did not make, since the `read` branch
swallowed it. The flag is what keeps the refactor a refactor.

**Shared control-entry state machine.** The design said harnesses recognize control entries;
what shipped also unified how they are *applied*. `wtft-parser.ts` now exports
`newParseStreamState()`, `applyControlEntry()` and `readControlEntry()`, and both
`parseSessionFile` and the daemon's `parseNewLines` drive the same state object. That deletes
the duplicated marker block the entanglement table called out (`wtft-parser.ts:418-447` **and**
`bin/wtft-daemon.ts:327-357`) instead of merely relocating it — the incremental and whole-file
paths can no longer drift.

Precedence note: every registered adapter is consulted per entry, first match wins, in registry
order (`claude-code` before `pi`). The pre-seam code checked Pi's markers first. The predicates
are disjoint on every real entry — they key on distinct `type` values and distinct top-level
fields — so the reordering is unobservable; a seam between harnesses that do not know about
each other cannot preserve a total order across them anyway.

**`getCurrentVersionTagPath()`** — a *writer-side* resolver alongside `getTagPath()`'s reader
fallback. Both prefer own-dir current, then sibling current; only the reader falls back to a
stale-version file. A writer must never open a stale-version filename — regenerating it is the
point of a version bump (#95) — so the daemon uses the writer form and derives its `tagsDir`
(takeover scan, version sweep) from the resolved path rather than from the session's directory.

**`resolveMovedSession()`** in `wtft-daemon-lib.ts` — the thin wrapper that asks every
registered harness where a vanished session id lives now. Both the daemon's poll loop and the
reap guard call it, so "moved vs deleted" is decided in exactly one place.

**`shutdown()` logs its reason** under `WTFT_DAEMON_DEBUG`. Found while testing: `shutdown`
took a `reason` string and discarded it, so "session moved" and "session removed" were
indistinguishable from outside — the one diagnostic this issue most needs. One line, and the
test asserts on it.

**`harnessLabel()`** replaces the two `c.harness === "claude-code" ? "Claude" : "Pi"` literals
in the selector; the label now comes from the harness. Relatedly `buildDisplayPath()`'s third
parameter widened from `"pi" | "claude-code"` to `string`, keying its Pi-specific `--`-slug and
date-prefix handling on `=== "pi"` and giving every other harness the generic treatment.
Without that widening, adding a harness would have required editing a shared file — the exact
thing the acceptance criterion forbids.

**Test seams.** `WTFT_CLAUDE_PROJECTS_DIR` and `WTFT_PI_SESSIONS_DIR` redirect the built-in
discoveries at fixture trees (the Codex sketch uses `CODEX_SESSIONS_DIR`). Without them the
union rule could only be tested against the real home directory.

**Registry memoisation.** `getHarnesses()` and `getParseAdapters()` cache their arrays, since
the parse path consults the adapter list once per transcript line. Every mutation
(`registerHarness`, `resetHarnessRegistry`, `loadExternalHarnesses`) invalidates both.

## The one deliberate behaviour change

Cache-miss observation (#152) now reads **normalized** usage, so Pi sessions get Cache Miss
dividers. Before the seam the check read `usage.cache_read_input_tokens` /
`usage.cache_creation_input_tokens` — Anthropic spellings only — while Pi writes `cacheRead` /
`cacheWrite`, so the divider was silently Claude-only. #152 specified an *observed* miss, and
the observation was always in the Pi log; nothing was reading it.

Everything else in the normalization is byte-identical on real data. The one place worth
checking was `Interaction.reasoningTokens`, which the old code read as `usage.reasoning` (Pi's
spelling) while the cost path accepted `reasoning_tokens ?? reasoning`. The seam collapses
these to one normalized field. Verified across 40 Pi transcripts: `reasoning_tokens` appears
**0** times and `reasoning` appears throughout, so the divergent case is unreachable.

## Roads not taken

- **Sweeping orphaned tag files.** With `getTagPath`'s sibling fallback they are found and
  used, so deleting them would throw away the *more complete* of the two artifacts — the
  opposite of the measured problem.
- **Inode-keyed daemon identity.** More faithful to "same file", but not derivable from a path
  the CLI holds before opening, and it does not survive a copy-then-delete move.
- **One full parser per harness.** Per-harness cost drift, and N copies of #52 Phase 3.
- **A pointer file written at the switch.** Only written if a parser happened to be running at
  that moment, which cannot be guaranteed. The transcript already carries the answer.
